## Q2 — eSTM JPJ enquiry / submission: which fields come from the UCD vs the buyer

Lead (verbatim): "Nothing in the request comes from whoever is logged in when it runs. All dealer-side values come from the UCD user saved on the transaction (ucdUserId) and that user's company account, which are read fresh each time the transaction is loaded. The scheduled job runs as "System"."

1. Seller company ID (enquiry, submission) → UCD company ID on the transaction (ucdCompanyId).
2. UCD company no / BRN (enquiry, submission, e-receipt) → UCD company Old or New BRN (useNewBrnOnJpj flag + retry).
3. UCD category → always "4" (built-in default).
4. Region code (enquiry) → UCD company state and city.
5. EVOC Representative ID (UCD) → IC (refId) of the transaction's UCD user, "*" removed.
6. Email1 (JPJ receipt) → eSTM JPJ receipt record email; if no consent date, UCD company primary user's email.
7. Email2 → eAuto's own jpjReceiptEmail setting.
8. EVOC owner email → transaction evocEmail if consent given, else UCD director email; EVOC "N" → fixed testevoc@eauto.my.
9. Buyer ID → company ROC for company / statutory / government buyers, else buyer IC/refId without symbols.
10. Buyer name + category → buyerName / company name + buyerCategory.
11. Address 1–3, postcode, district, state (submission) → buyer mailing address. No dealer address sent.
12. EVOC Representative ID (Company) → buyer refId, company buyers only; else blank.
13. Dealer data re-read each load → profile changes after creation change what is sent.
14. Non-POO payment option uses a separate commit request (not read).

## Q3 — Jobs / listings that pick STMS or eSTM rows (risk of picking up a new type)

Lead (verbatim): "None of these selections filter on a transaction type or category. They pick rows only by status columns, flags, dates and company, so a new type stored in the STMS or eSTM tables would be picked up whenever its status values match."

1. StmsJpjSubmissionJob → STMS status Pending, last payment Paid, last JPJ enquiry Passed, last submission Pending; not Draft; cancelFlag not true; lastBkStatus "RTN Success"/"RTN Pending". All submitted to JPJ.
2. EstmJpjSubmissionJob → same + lastUpdatedAt ≥ 20 min old. Payment option POO → JPJ submit; anything else → JPJ "commit" path (a non-POO new type would be committed by default).
3. JpjExpiryNotificationJob / APT creation → latest Approved STMS row (status 2) for buyer company + plate, newest jpjApprovedAt; no aptTransactionId → APT created and linked.
4. Wholesale APT screen → same "latest Approved STMS row for company + plate" lookup.
5. STMS cancellation reminder popup → reads no rows; hard-coded April–June 2024; never opens (not in dialog order, no flag set).
6. Bulk JPJ enquiry list → STMS Failed (3) with last enquiry code 4K, own company (and branch if branch-only).
7. Bulk JPJ enquiry results / export → no status filter; only passed IDs.
8. Bulk payment list → STMS Pending + payment New + submission New, or Failed + payment Failed + submission New; last enquiry Passed/Approved.
9. BO JPJ resubmission (STMS, eSTM) → operator-picked statuses; ignores lastBkStatus and cancelFlag.
10. BO eSTM resubmission "Pending" mode → older eSTM submission query + payment-date range.
Things to watch (verbatim): "Auto-submission: a new type that reaches Pending / Paid / Passed / Pending with an RTN bank file status goes to JPJ automatically."
