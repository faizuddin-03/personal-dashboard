EAINT-12167
Allow Ops to Input Device SN on Device Purchase SR Info Page When Updating Delivery Status to Arranged
Status Code Review Priority Medium Assignee Lim Yi Link SRD v1.2 · 17 Aug 2026 Environment not yet confirmed

Overview

Adds two fields to the shipping-details update flow for a Device Purchase Service Request — Number of Device and Device Serial No. — so Ops can record each device's serial number before marking delivery Arranged. This SN is what EAINT-12166's Delivery Order prints.

Portal & where the changes live

Portal
BackOffice
Module
Service Hub — Biometric Device Purchase & Software Installation
Primary page
Biometric Device Purchase & Software Installation Listing → Service Request Details — two new fields under Consignment Number
Also touches (v1.2)
The Listing itself — now shows Number of Device / Device Serial No. per record

Why

No field exists today for Ops to capture a device's serial number, so EAINT-12166's Delivery Order PDF has nothing to print in that slot. This closes that gap.

The mid-SRD pivot

A dev-review comment (zhan.choon → Lim Yi Link, 12 Aug 2026) questioned the original design before build started. Three questions were raised; the SRD's final shape (v1.1 onward) reflects the answers — worth knowing when reading the requirement list below, since struck-through acceptance criteria in the SRD trace back to this thread.

v0.1–v1.0 design

Number of Device: a manual dropdown, Ops picks 1–10. One SN field generated per unit selected.

→

v1.1 onward (current)

Number of Device: auto-filled from the order, disabled, view-only, no ceiling. SN field count always matches it — 13 devices means 13 fields.

What's new — requirement manifest

REQ-001
upd. v1.2

Number of Device — new field

Displays under Consignment Number. Auto-filled with the quantity purchased in the same transaction. Disabled — view only, no free text.

v1.2 clarified: the value shown is the transaction total, not the quantity on a single device record — matters once you cross-check against the Listing (REQ-011 below).

REQ-002
upd. v1.1

Validation specs

Dropdown selection, 1–10 units → Auto-filled by system, disabled, mandatory, no free text entry.

REQ-003
upd. v1.1

Serial No. field generation

One Device Serial No. field per unit — count always matches Number of Device. Example: 13 devices → 13 fields, numbered 1–13. No 10-field ceiling.

REQ-004

Serial No. — validation

8–12 characters, alphanumeric, spaces allowed, no special characters, English only, mandatory.

REQ-005

Serial No. — input handling

Special characters strip automatically as typed. 12 characters is a hard stop. Below 8 on save: "Device Serial No. must be between 8 and 12 characters."

REQ-006

Field availability by status

Editable only while Delivery Status = New. Read-only once the status has moved past New.

REQ-007
upd. v1.1

Mandatory check on save

Number of Device not selected — struck out, no longer a valid scenario now that the field auto-fills. Every Serial No. field left blank still blocks save: "This field is required."

REQ-008

Triggers the EAINT-12166 flow

Saving with every field complete + Delivery Status set to Arranged triggers EAINT-12166's Delivery Order generation. An incomplete field blocks the status change entirely — the flow never fires half-done.

REQ-009

Access restriction

All Hub Admin users get access to the new fields, except an 18-account blocklist. Per the dev's confirmed comment, these accounts are already blocked from the "Update Shipping Details" function today — no code change needed for them.

REQ-010
v1.1

UI display on the popup

"Device Serial No." field group, labelled and marked mandatory, sits directly below Number of Device. Fields number sequentially from 1, laid out two per row, left to right, inside a scrollable area once they exceed the popup's visible height.

REQ-011
v1.2

Record display in the Listing

Each device purchased in one transaction gets its own row in the Listing. Every row shows Number of Device = 1 and one Serial No. — not the transaction total. Example: 10 units purchased → 10 rows, each showing "1" and its own serial.

Open — not resolved in the SRD

  • What happens when Ops mistypes a locked Serial No.? The comment thread offered two options — A: accept it, fix via an IT support ticket; B: let a senior Hub Admin correct it even after Arranged (extra build work). SRD v1.2 never states which was picked. Flag to Lim Yi Link or dev before writing a test case for this scenario — don't assume either option.
  • Duplicate-SN rejection — "no two devices share a serial" is described in the comment thread as an intended build rule, but it isn't restated as a formal requirement row or acceptance criterion anywhere in the SRD body. Confirm it actually made it into the build before relying on it.

Important for QA

  • This ticket gates EAINT-12166 — its flow only fires the Delivery Order once SN entry + Arranged status succeed together in one save.
  • Check the 18-account blocklist against real BO test logins — those accounts should not see the new fields at all, not just be unable to edit them.
  • Test the boundary values on Serial No. directly: 7 chars (reject), 8 (accept), 12 (accept), 13 (blocked at input), and a stray special character (auto-stripped, not rejected).
  • Test field-count-follows-quantity at both ends: 1 device (1 field) and a double-digit purchase like 13 (13 fields, two-per-row, scrollable) — the old 10-field ceiling is gone as of v1.1.
