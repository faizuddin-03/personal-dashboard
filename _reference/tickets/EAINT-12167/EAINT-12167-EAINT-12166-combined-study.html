EAINT-12166

Enable DO Creation for Device Purchase, with Interim Upload Space (upload space dropped from scope, see below)

Assignee: Chee Mei Jia

Overview

Adds a one-click "DO" button on the Device Purchase Transaction Details page that auto-generates a Delivery Order PDF, reusing the existing DO template from Company Management. Removes manual DO prep entirely. The "interim document upload space" named in the ticket title was dropped from scope as of SRD v0.4 — confirmed with the requestor. Don't test it, and don't be confused by the ticket title.

Click-through flow (BackOffice)

Derived from the SRD plus a working client-side mockup (eAuto_BackOffice_Existing_Mockup_20260818.html, a real jsPDF generator, not a wireframe) — not yet confirmed against a live build, nothing has been pushed to any environment for this ticket yet (see Teams status above).

1

Open Biometric Device Purchase & Software Installation Listing, select a Device Purchase transaction → Transaction Details.

A new "DO" button appears next to INVOICE / e-INVOICE in the top action row — on Purchase-only and Purchase+Installation transactions only; correctly absent on Installation-only SRs (out of scope for this CR).

2

Update the consignment note (existing action).

Per REQ-001 this is the actual generation trigger. Not modeled by the mockup — its DO button is always clickable against static pre-filled data, so the pre-consignment-note state and both REQ-006 error messages ("required details are incomplete" / "could not be generated") can't be exercised until a live build exists. Per dev's own QA guide: the DO is created after BO clicks [Update] in the Update Shipping Details dialog — specifically the save that moves Delivery Status New → Arranged, not a separate consignment-note-only action.

3

Click DO.

PDF downloads immediately, auto-populated from the transaction record — company, payment, and device details, zero manual entry (REQ-002).

4

Check the PDF for a ≤20-unit transaction.

Single page, one Delivery Order Number. For 21–40 units: 2 pages in one PDF, two Delivery Order Numbers (e.g. DP-0001, DP-0002), serials numbered continuously across the split, each page showing its own count + "Split order · N of 2" (REQ-003 — verified exactly against the mockup's generator).

5

Edit the company name, address, tel, or recipient elsewhere, then re-download the same DO.

Re-download must return the original values as at generation time (REQ-008 snapshot rule) — not the edited ones.

  • The 20/40-unit split boundary needs explicit coverage: 20 (no split), 21 (20+1), 25 (20+5), 40 (20+20) — verify split numbering, continuous serials, per-DO counts.
  • The snapshot rule (REQ-008) is easy to miss on a happy-path pass — requires a mid-test data edit, re-download, and diff against the original.
  • 21 fields are mapped field-by-field to their data source in SRD §2.2.5 — use it as the field-level checklist.
  • Mockup vs SRD field-mapping gaps (don't take the mockup's layout as final): it combines Company Name and Company Reg. No. into one row, where the SRD's §2.2.5 table lists them as two separate DO fields; its Payment Ref./Date text omits the "REF"/"DATED" wording the SRD's sample value shows literally; and "Issued by — Name" is hardcoded to one sample name rather than the actual BackOffice user who keyed the serial. Verify all three against the real build.

3

4

EAINT-12167

Allow Ops to Input Device Serial Number on Device Purchase SR Info Page

Assignee: Lim Yi Link

Overview

Adds two fields to the shipping-details update popup for a Device Purchase Service Request: an auto-filled, locked "Number of Device," and one "Device Serial No." box per unit. Ops fills serials while Delivery Status = New; saving with status set to Arranged triggers EAINT-12166's DO flow. This is the upstream data source 12166 depends on.

The mid-SRD pivot

SRD v1.0 originally specified a manual 1–10 dropdown for Number of Device. The dev review thread (12 Aug) pushed back: the system already knows the paid quantity, and Ops picking a different number would contradict the listing (which already shows one line per device purchased). Settled in v1.1: the field is now auto-filled from the order and view-only. The unit cap was also raised from 10 to 40 in the same round of Teams discussion (14–17 Aug) — a parcel still ships at most 10 devices, so a full 40-unit order is expected to go out across several parcels.

Click-through flow (BackOffice)

What a Hub Admin actually clicks through, end to end, and what happens after each step.

1

Log in to BackOffice as a Hub Admin account not on the 18-account blocklist (REQ-009).

Blocklisted accounts are already excluded from the function that follows — no new restriction, just a pre-existing gate.

2

Open Biometric Device Purchase & Software Installation Listing and select the Service Request → Service Request Details.

Details page shows the existing shipping fields (delivery date, consignment number, Delivery Status) plus the device quantity paid for on the UCD side.

3

Click Update Shipping Details.

Popup opens. Number of Device now appears directly under Consignment Number — auto-filled with the order quantity, disabled, no free text.

4

Scroll to Device Serial No., below Number of Device.

One empty, mandatory box per device, numbered 1–N, laid out two per row; the box area scrolls once the count exceeds the popup's visible height.

5

Key in each device's serial number (8–12 chars, alphanumeric + spaces).

A typed special character is stripped automatically, not blocked. Below 8 chars on save: "Device Serial No. must be between 8 and 12 characters." A serial already used elsewhere (same request or another) is expected to be rejected as a duplicate — a build rule from the dev comment thread, not yet reconfirmed live.

6

Set Delivery Status to Arranged (or leave at New if not shipping yet).

Any Serial No. box left blank blocks the status change entirely — "This field is required." The flow never fires half-done.

7

Click Save.

If every field is complete and status = Arranged: the record saves and EAINT-12166's Delivery Order flow becomes available — the "DO" button on the Transaction Details page can now generate the PDF using these exact serials. If status is still New: the serials just save, fields stay editable.

8

Reopen Update Shipping Details after an Arranged save.

Number of Device and every Serial No. box are now read-only — no edit control appears for anyone, including a senior Hub Admin. resolved Confirmed via Teams (17 Aug): a mistyped serial at this point is fixed only by raising an IT support ticket — see the resolved item under Open questions below.

9

Check Biometric Device Purchase & Software Installation Listing.

One row per physical device in the transaction (v1.2) — each row shows Number of Device = 1 and its own single serial, never the transaction total.

Concurrency — questions for dev, not yet candidate TS

Neither SRD says anything about concurrent access. This is error guessing, not one of the three CTFL shapes used above — doesn't fit EP/BVA, a decision table, or a state table, so it isn't forced into one. Most of these need either two testers clicking in coordinated real-time or a script firing parallel requests to actually trigger — hard to hit reliably by hand, and none of them are answerable without dev confirming what locking/idempotency exists server-side. Treat as questions to put to dev before any of these become scripted TS.

EAINT-12167 · unconfirmed

Same-SR concurrent save. Two Hub Admins open Update Shipping Details on the same SR at once, both key in serials, both Save — does the second save silently overwrite the first, or is there a conflict warning/lock?

EAINT-12167 · unconfirmed

Duplicate-SN race. Two Ops key the same serial number onto two different devices at nearly the same instant — does the duplicate-SN check catch it (a real DB constraint), or is there a race window where both saves succeed?

EAINT-12167 · unconfirmed

Lock-mid-edit race. User A saves with status → Arranged (locking the record) while User B still has the popup open mid-edit on the same record — what happens to B's in-flight save after A's lock takes effect?

EAINT-12167 · unconfirmed, gated on the shared-vs-per-SR structural question

Multi-device concurrent edit. If a multi-device transaction really is "one shared shipping update covers all devices" (still open — see Open Questions above), two Ops touching different device-rows of the same transaction concurrently could clobber each other. Needs that structural question answered first before this is even well-formed.

EAINT-12166 · unconfirmed

Double-generation race. Two users click "DO" on the same transaction before it's ever been generated — does generation fire twice (two DO Numbers created), or is the first generation idempotent/locked so the second click just downloads the same PDF?

EAINT-12166 · unconfirmed

Split-numbering collision. If the above race did fire generation twice on a split-order (21–40 units), could DP-000X numbering collide or duplicate across the two concurrent attempts?

EAINT-12166 · unconfirmed, low risk

Concurrent re-download. Two users re-downloading an already-generated DO at the same time — should be safe/read-only, worth a quick confirm both get identical bytes.

EAINT-12166 · unconfirmed

Snapshot-timing race. Company info is edited in Account Management at the exact moment generation is firing (REQ-008 snapshot) — does the snapshot capture pre- or post-edit data if the timing overlaps generation itself?
