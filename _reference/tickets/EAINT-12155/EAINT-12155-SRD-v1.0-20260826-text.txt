2.0  REQUIREMENT 
 
2.1  High-Level Requirement Overview 
# 
Item 
Description 
2.1.1 
 
Enhancement Overview 
 
Strengthen the eAuto password policy and apply it to newly created 
accounts across all portals. Every password set for a new account, 
whether entered by an administrator or system-generated, must be at 
least 12 characters and must contain an uppercase letter, a lowercase 
letter, a number, and a special character. 
 
2.1.2 
 
Key Value(s) Expected 
 
1. Reduce the risk of account compromise caused by weak or short 
passwords. 
2. Remove the inconsistent password rules currently duplicated across 
multiple classes. 
3. Close the flows that today accept a password without any server-side 
validation. 
4. Replace weak system-generated passwords with policy-compliant 
ones. 
 

===== PAGE 7 =====
# 
Item 
Description 
2.1.3 
 
Additional Note(s) 
 
The policy applies to accounts created on or after the deployment date 
only. 
 
Existing accounts are exempt. Stored passwords remain valid, no forced 
password migration is performed, and an existing user is never required 
to change a password that does not meet the new policy. 
 

===== PAGE 8 =====
2.1.1  Assumptions 
# 
Assumption 
1 
 
Existing stored passwords remain valid after deployment. No forced password migration is carried out for current users, 
and an existing user is never prompted to change a non-compliant password. 
 
2 
 
A single validation utility is introduced as the source of truth for the password policy, and all server-side call sites 
delegate to it. 
 
3 
 
The My Account password change and the Change Main User Password pages hash the password in the browser before 
submission, so the server never receives the plaintext. Client-side validation is the accepted enforcement point for these 
two pages. 
 
4 
 
All other password flows submit the plaintext password to the server and can therefore be validated server-side. 
 
5 
 
The client-side and server-side hashing implementations agree only on printable ASCII input, so non-ASCII characters 
must be blocked to avoid permanent lockout. 
 
6 
 
The system can distinguish a newly created account from an existing account, so that the policy is applied to new 
accounts only. The mechanism for this distinction is to be confirmed with the development team.

===== PAGE 12 =====
2.2.2  Existing Issue & Expected Behaviour 
# 
Item 
Description 
1 
 
Existing Issue / Behaviour 
 
1. The minimum length is 6 characters, and 8 for AATF and Insurance. No uppercase, 
lowercase, number or special character is required. 
2. The rule is duplicated across several classes and two copies contain a logic error 
that lets almost any password pass. 
3. Several flows have no server-side validation, including company creation and the 
AATF company pages. 
4. System-generated passwords are weaker than the policy itself. 
5. A password containing & = + % # corrupts the login request parameter. 
 
2 
 
Expected New Handling / 
Behaviour 
 
1. One policy applies to every portal: minimum 12 characters with at least one 
uppercase letter, one lowercase letter, one number and one special character. 
2. Spaces are rejected and only printable English characters are accepted. 
3. A single validation utility is introduced and every server-side flow delegates to it. 
4. System-generated passwords comply with the policy. 
5. A password containing special characters is accepted correctly at login.

2.2.4  Password Policy Rules 
The rules in this section apply when a password is set for a newly created account. Accounts existing before the deployment date 
are exempt. 
 
# 
Requirement ID 
Item 
Description 
Acceptance Criteria 
1 
 
EAINT-12155-
REQ-001 
 
Existing Account 
Exemption 
 
The password policy shall apply to 
accounts created on or after the 
deployment date only. The existing 
stored passwords shall remain 
unchanged. Upon login, an existing 
user shall be able to sign in with the 
current password even if it does not 
meet the new policy, and shall not be 
prompted to change it. 
 
An existing account with a legacy 
password logs in successfully after 
deployment, is not forced to change the 
password, and is not shown any policy 
message.

the password is not updated.
