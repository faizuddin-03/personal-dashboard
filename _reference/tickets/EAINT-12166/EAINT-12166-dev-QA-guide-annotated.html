EAINT-12166 — Delivery Order for Device Purchase

BackOffice downloads a system-generated Delivery Order (DO) PDF for a Biometric Device Purchase. This release also changes how DO numbers are issued (per-day sequence, race-safe), stores the PDF once at issue (frozen snapshot), and moves the Report Engine URL into settings — the reason for the dedicated regression section at the bottom. Reference layout: the four approved draft DO PDFs.

Highlighted = new information or a correction vs. what the SRD/mockup led us to expect this session, before reading this guide. Everything else confirms the SRD as already understood.

Before you test

  • Deploy team applied sql/2026-08-17-EAINT-12166/master.sql — it creates the DO tables and counter, runs its own pre-deploy duplicate check (must return zero rows) and the one-time seeding.
  • Report Engine redeployed with the DO template, and settings.eauto.report.engine.api.url set correctly for the environment.
  • You need a UCD account and BackOffice access. Tests below create fresh paid device purchases.

1 · Purchase page — quantity cap

#StepsExpected
1.1Type 41 or more in the quantity box.Value clamps to 40 and the message "A maximum of 40 devices can be purchased per transaction." appears.
1.2Type exactly 40.No message — 40 is valid.
1.3Clear the box / type 0 and leave the field.Value becomes 1, no error left behind.
1.4Try to submit > 40 bypassing the UI (browser console).Server rejects it — the cap is enforced server-side too.

2 · DO numbers — issued once, at the shipping save

Numbers come from the new per-date counter (yyyyMMdd/DP-0001), restarts each day; a save after 12:00 noon is dated the next day. Issued once at the first shipping save and never change afterwards.

#StepsExpected
2.1Pay a ≤ 20-unit order; save shipping (serials) in BO.Exactly one DO number appears on the detail page.
2.2Pay a 21–40-unit order; save shipping.Two consecutive DO numbers (units 1–20 on the first, the rest on the second).
2.3Same day: ship a 40-device order, then a 5-device order.Numbers run in sequence — no repeats (e.g. 0001 + 0002, then 0003).
2.4Have a different officer update the transaction later (e.g. mark Delivered). Download the DO again.Same numbers; Issued-by still the original officer's full name (not the login id) and the original date — nothing re-issues.
2.5(Next calendar day) Ship another order.Numbering restarts at .../DP-0001 under the new date prefix.

3 · The DO PDF — content and layout

#StepsExpected
3.1Click the DO button on a shipped order.PDF downloads as Delivery_Order_<SR ref>.pdf. Layout matches the approved drafts: logo top-left, bordered tables, English + Malay labels, issuer name + "ADMIN", warranty remark.
3.2Order of ≤ 20 devices.1 page; all serials in the grid; selected appointment slots listed.
3.3Order of 21–40 devices.One PDF, 2 pages, each page its own DO number, max 20 serials per page.
3.4Order with no appointment slot selected.Appointment area shows: "No appointment has been selected yet — to be arranged with the UCD."
3.5Order with extra installations.Installation count printed in words = quantity + extra installations. Never blank, never "FREE".
3.6Account with a long multi-line registered address.The DO shows the registered account address (never the delivery address), complete — nothing cut off.

4 · Stored PDF — frozen snapshot

The PDF is generated once at the shipping save, stored, and every later download serves that stored copy.

#StepsExpected
4.1Edit the company profile (address / phone) after shipping, then download the DO again.Identical PDF — still the old details. The snapshot is frozen at issue time.
4.2Download twice in a row.Identical file both times; one BO audit-log entry per download listing all DO numbers of the transaction.

5 · Display — BO detail and UCD receipt

#StepsExpected
5.1Open BO detail of a split (2-DO) order.Delivery Order Number shows both numbers, comma-separated.
5.2Open the same order's UCD receipt page.Same display as BO — all numbers, comma-separated.
5.3Open an unshipped (New) order on both pages.DO number shows "-"; no DO button.
5.4Open a device purchase created before this release.Page opens normally and shows its old DO number, but has no DO button (by design — legacy orders don't carry the data the PDF needs).

6 · Failure behaviour

Needs the Report Engine stopped briefly — arrange with the deploy team.
#StepsExpected
6.1Report Engine stopped: save shipping on a paid order.Save succeeds — status, serials and DO numbers all assigned. Only the stored PDF is skipped.
6.2Still stopped: click the DO button.Within a few seconds: "Delivery Order could not be generated. Please try again." — no endless loading, no raw error page. If required details are missing: "Unable to generate Delivery Order: required details are incomplete."
6.3Start the Report Engine; download again on the 6.1 order.PDF generates live and downloads fine (no stored copy exists for that order — accepted: it live-generates from then on).

7 · Regression — Report Engine URL moved to settings

NEEDS A DECISIONRun in every environment (SIT, staging, prod smoke). Five existing report flows previously called a hardcoded http://localhost:8088; they now all read settings.eauto.report.engine.api.url. A wrong or missing value in one environment breaks all of them at once — so each PDF below must be generated once per environment after deploy.
#Report flowWhat to doExpected
R1Insurance — e-ContractGenerate an insurance e-Contract PDF (with and without signature).PDF downloads and looks as before.
R2Insurance — CP58Generate a CP58 PDF.PDF downloads and looks as before.
R3Insurance — Add User AuthorizationGenerate the Add User Authorization PDF and its Declaration PDF.Both download and look as before.
R4eSTM — Buyer AuthenticationComplete an eSTM buyer authentication that produces the PDF slip.Slip generates as before.
R5Company Management — Print DO (New Registration)Use the existing manual Print DO form under Company Management.Prints as before — this old form is unchanged apart from where it reads the URL.

One-minute config check per environment: the edition's settings.properties must contain settings.eauto.report.engine.api.url pointing at that environment's Report Engine host. The Report Engine serves at the root (no context path), so the value is host + port only, e.g. http://localhost:8088 where co-located.

9 · Device Serial No. capture — Update Shipping Details dialog (EAINT-12167, ships on this branch)

#StepsExpected
9.1Open Update Shipping Details on a paid device purchase of N devices.Dialog shows "Number of Device: N" and exactly N numbered Device Serial No. inputs in two columns; the dialog body scrolls when N is large (up to 40).
9.2Leave one serial blank → Save.Red "This field is required" under that input; nothing saved.
9.3Type a 7-character or 13-character serial → Save."Device Serial No. must be between 8 and 12 characters." under that input.
9.4Type a serial with a symbol (e.g. ABC-12345) → Save.Rejected — letters, digits and spaces only.
9.5Type the same serial in two inputs → Save."Duplicate device serial number. Each serial number must be unique."
9.6Fill all N serials validly, status Arranged, consignment + date → Save."Shipping details saved." Detail page lists every serial; DO number(s) assigned (section 2); serial inputs, Consignment No. and Delivery Date become read-only (locked once Arranged).
9.7Open the dialog again on that Arranged order.Serials shown greyed / not editable; only the status move Arranged → Delivered is offered.
9.8Try Delivered → Arranged (or New) via the browser console."Invalid delivery status change. Delivery status can only move New → Arranged → Delivered."
9.9BO Service Request listing.No serial column; everything else as before.
