EAINT-12166
Enable DO Creation for Device Purchase, with Interim Document Upload Space
Status Code Review Priority Medium Assignee Chee Mei Jia SRD v1.1 · 28 Aug 2026 Environment not yet confirmed

Overview

BackOffice has no way to produce a Delivery Order (DO) for a Device Purchase transaction today. This change adds a one-click "DO" button on the transaction's details page that auto-generates the DO as a PDF, reusing the template already used under Company Management.

Portal & where the changes live

Why

Removes manual DO preparation — BackOffice produces a ready Delivery Order in one click instead of a person assembling it by hand.

What's new — requirement manifest

REQ-001

Auto-generation & download

DO is generated by the system when the BackOffice user updates the consignment note. Clicking "DO" downloads it as a PDF.

REQ-002

Auto-populate, no manual entry

Fields are populated from the transaction record — company, payment, and device details — with zero manual input.

REQ-003

Device Serial Number & the 20/40 split

Max 20 serials per DO. A transaction up to 40 units splits into up to 2 DOs (blocks of 20, remainder on the last — e.g. 25 → 20 + 5), combined in one PDF of at most 2 pages. Serials run continuously across the split (e.g. ZF 00000021–00000040). Each DO shows its own DO number, its own device count — not the transaction total — and a "Split order · N of M · X units total" annotation.

Serial number itself is sourced from EAINT-12167 — the SN Ops keys in there. hard dependency

REQ-004

Remarks

Defaults to "Device warranty 1 year".

REQ-005

PDF output

Matches the existing Company Management Delivery Order layout exactly.

REQ-006

Error handling

Incomplete transaction data blocks generation: "Unable to generate Delivery Order: required details are incomplete." A system/generation failure shows: "Delivery Order could not be generated. Please try again."

REQ-007
v1.1

40-unit purchase cap

On UCD Step 1, "+" disables at 40; a manually keyed value over 40 is corrected to 40 on blur with: "A maximum of 40 devices can be purchased per transaction." "−" stays enabled at 40. This is what guarantees a generated DO never exceeds 2 pages.

REQ-008
v1.1

Data snapshot, never refreshed

DO fields are fixed at the moment of generation. Later edits to Company Name, Reg. No., Address, Tel, Recipient Name/Phone in Account Management do not update an already-generated DO. Re-downloading returns the exact original PDF — no background sync exists.

Explicitly out of scope

  • Changes to the existing "Print DO" feature under Company Management
  • DO generation for transaction types other than Device Purchase
  • DO Type = New Registration (handled under a separate request)
  • The interim manual document-upload space named in the Jira ticket title — dropped from scope as of SRD v0.4, confirmed with the requestor
  • Email notification on DO generation — confirmed not required, 14 Aug 2026

Important for QA

  • EAINT-12167 is a hard dependency — its Device Serial No. is what this DO prints. Test it first, or in tandem.
  • Cover the 40-unit boundary explicitly: 20 (no split), 21 (20+1), 25 (20+5), 40 (20+20). Check split numbering, continuous serials, and that each DO shows its own count, not the transaction total.
  • Test the snapshot rule directly: generate a DO, edit the company's name/address/tel/recipient afterward, re-download the same DO — it must still show the original values.
  • The ticket summary still says "interim document upload space" — don't test that; the SRD dropped it from scope two drafts before baseline.

Where these details must match — cross-page checklist

The Delivery Order's data comes from several pages and one upstream ticket before it's ever printed. Same company name, same device count, same serials — check every surface below reads identically, and that the PDF itself never drifts from what generated it.
