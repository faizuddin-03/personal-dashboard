01 Environment & test accounts

Two apps, one browser session, no separate login for BackOffice — you always enter through core.

Signature is per person, not per role

Log in as a user for the very first time they approve/review anything → a signature pad is mandatory. Every later action by that same user (any month, any role they hold) reuses the stored PNG silently. Plan your test order so you see the pad exactly once per test user.

02 Getting test data onto a month — the month-close job

The listing shows nothing for a month until it's closed — a scheduled job (or a manual trigger you can use directly) freezes that month's counts × rate into a snapshot. Nothing on the page is ever live-computed.

TriggerHowUse it for
Manual, fastest for QAGET {eauto-cron}/eautocron/sys/manual/association-payment-month-close/{year}/{month}Force-close any past month on demand instead of waiting for the 1st-of-month schedule.
Machine (what core/cron actually call)POST /ext/association/{year}/{month}/close (X-API-KEY)Reproducing the exact call path if the manual endpoint isn't available in your box.
Real scheduleeauto-cron, 00:05 on day 1Don't wait for this in normal testing — use the manual trigger above.

The three states you'll see per month on the summary listing

  • "–" not yet closed — no snapshot exists yet. No figures, no actions available. Confirm this is what an un-closed month looks like before you close one, so you know what "before" looked like.
  • "0.00" closed, no data — closed, but no qualifying transactions that month. Confirm the workflow buttons still work on a zero-amount month (don't assume zero = broken).
  • Real figures, closed — ready to review and approve; this is the main path.

What counts toward a month's figures (so you can sanity-check a number, not just eyeball it): approved + paid STMS/eSTM/APT transactions, counted by JPJ Approved Date (not created date), grouped by the dealer's registered state (not the vehicle's plate state), split into cars (CAR+COMM_CAR, RM1.00 each) and motorcycles (BIKE+COMM_BIKE, RM2.00 each).

03 Test cases by SRD requirement

One case per requirement ID, straight from the SRD's own acceptance criteria. Click each to expand the steps. P1 = core happy-path/gate, must pass before sign-off. P2 = important edge case. P3 = nice-to-confirm.

REQ-001 New Reports menu entry P1
  1. Log in to core as any user with access to BackOffice.
  2. Open the Reports menu.
Expect: "Association Payment Listing" appears under Reports; clicking it lands you on the BackOffice summary page, already authenticated (no second login).
REQ-002 Year filter + Search P2
  1. On the summary page, set the Year filter to 2026 and click Search.
  2. Try a year with no closed months at all.
Expect: case 1 shows 2026's 12 months; case 2 shows all 12 months as "not yet closed", not an error or empty page. Year options start from 2026 only.
REQ-003 Role resolved from login ID, not a picker P1
  1. Log in as eautozara (Drafter-only) and open a closed month's details.
  2. Log in as mfizni (all three roles) and open the same month at each workflow stage.
  3. Log in as a user with no role row at all and try to open the details page directly by URL.
Expect: case 1 shows only Drafter actions, no role dropdown anywhere. Case 2 shows the actionable block for whichever role's turn it currently is. Case 3 → 403, even though the Reports menu link was visible in core.
REQ-004 Monthly rows: Car/Motorcycle counts + RM, by JPJ Approved Date P1
  1. Close a month with a known set of approved+paid transactions (or use existing seeded data).
  2. Compare the listing's Car Transactions / Cars (RM) / Motorcycle Transactions / Motorcycles (RM) against a manual count from core's own Transaction Summary Report by State for the same month.
  3. Check the year-to-date/full-year total row sums the 12 months correctly.
Expect: all 12 months listed; figures match core's report exactly (same source data, same JPJ-approved-date window); RM = count × rate (RM1.00 car, RM2.00 motorcycle); total row = sum of the 12 rows.
REQ-005 Workflow status columns P2
  1. Walk one month through Drafter Approve → Reviewer Approve → Approver Approve, checking the summary row after each step.
  2. Walk a second month through Drafter KIV, and a third through a Reviewer Reject.
Expect: Drafter Status cycles Pending→Approved / KIV / Review Again as appropriate; Reviewer Status Pending→Approved/Review Again; Approver Status only ever Pending→Approved. No status value outside this set ever appears.
REQ-006 Finance Payment Date column P3
  1. Check the column before Approver action, and again right after.
Expect: shows "-" before Approver approval; shows the picked date as DD-MM-YYYY (e.g. 31-07-2026) immediately after.
REQ-007 View action P3
  1. Click View on any month row.
Expect: opens that month's details page (state breakdown + workflow for that specific month, not another one).
REQ-008 State-level breakdown — all 16 states + TOTAL P1
  1. Open a closed month's details page.
  2. Count the state rows and check the formatting of a non-trivial amount.
Expect: exactly the 16 states listed (Johor → Putrajaya, per the SRD's numbered list) plus a TOTAL row that equals the sum of the 16. Amounts formatted #,##0.00 (e.g. 38,785.00). Car and Motorcycle figures shown separately, never combined into one number.
REQ-009 Sequential approval enforced P1
  1. Before Drafter acts, log in as Reviewer and try to act on the same month.
  2. Before Reviewer acts, log in as Approver and try to act.
Expect: the later role's action buttons are disabled with a waiting note in both cases — never clickable out of order. Forcing the underlying URL/request directly (not just the UI) should also be rejected server-side, not merely hidden client-side.
REQ-010 Drafter: Approve or KIV P2
  1. Approve one month as Drafter.
  2. KIV a different month as Drafter.
Expect: Approve → Drafter Status = Approved, Reviewer unlocked. KIV → Drafter Status = KIV, workflow parked (note: there is currently no un-KIV path — a KIV'd month stays KIV; confirm this matches what the business expects, it's a known open item, not something to test a resolution for).
REQ-011 Reviewer: Approve or Reject (remarks mandatory) P2
  1. Approve a Drafter-approved month as Reviewer.
  2. Reject a different one, first trying to submit with an empty remarks field.
Expect: Approve → Reviewer Status = Approved. Reject with blank remarks is blocked client- and server-side; with remarks filled in, the month bounces back with Drafter Status = "Review Again" and the remarks visible in the audit log.
REQ-012 Approver: Approve or Reject (remarks mandatory) P2
  1. Approve a Reviewer-approved month as Approver.
  2. Reject a different one with remarks.
Expect: Approve proceeds straight to the payment-date picker (REQ-013). Reject returns the month to the Reviewer with Reviewer Status = "Review Again" and the remarks logged.
REQ-013 Finance payment date — future-only, picker-only P1
  1. As Approver, approve and pick a future date from the on-screen picker.
  2. Try to submit with the field empty.
  3. Try to select today's date or a past date (if the picker allows navigating there).
  4. Try to type or paste a date directly into the field (not via the picker) — e.g. via keyboard input or a pasted string.
Expect: case 1 saves normally. Cases 2 & 3 are rejected with a validation message; approval does not complete. Case 4 is blocked entirely — the field only ever accepts a picker selection, confirm typed/pasted input has no effect on the stored value.
REQ-014 On-screen e-signature, captured once P1
  1. As a test user acting in a role for the very first time, trigger an Approve action.
  2. Have that same user perform a second approval (different month, same or different role they hold).
Expect: case 1 shows the signature pad and blocks completion until something is drawn. Case 2 does not show the pad again — the stored signature is silently reused.
REQ-015 Audit log — every transition recorded P2
  1. Walk a month through Drafter Approve → Reviewer Reject → Drafter re-Approve → Reviewer Approve → Approver Approve.
  2. Open the audit log on the details page after each step.
Expect: one row per transition, each with date/time, role, action/status, remarks (when applicable), and — for approvals — a signature record and, for the Approver, the payment date. Log entries appear in order and none are skipped/merged.
REQ-016 Payment Request download gated on full approval P1
  1. On a month that is NOT yet fully approved, look for the FMC/MMSDA download buttons.
  2. Fully approve a month (all three roles), then check again.
  3. With the month not fully approved, try hitting the download URL directly (bypassing the UI).
Expect: case 1 — buttons hidden, pending note shown ("...available for download once the Drafter, Reviewer and Approver have all approved."). Case 2 — both buttons appear and download successfully. Case 3 — 403, not a partial/blank file.
REQ-017 / REQ-018 / REQ-019 Payment Request document format & field mapping (FMC + MMSDA) P1
  1. Download both FMC and MMSDA for a fully-approved month.
  2. Check the file name against the required format.
  3. Check every field on both documents against the SRD's fixed/flexible mapping tables (§2.2.10 / §2.2.11).
  4. Re-download the same document a second time.
Expect: filenames match Payment Requisition_<Association>_<Month><Year>.pdf (e.g. Payment Requisition_FMC_August 2026.pdf). All "Fixed" fields match the SRD verbatim (company header, To/Attn "Marie Ann"/Adds, vendor bank details — different per association). All "Flexible" fields are correctly sourced: dates as DD-MM-YYYY, amount in figures and matching amount in words, each Prepared/Checked/Approved-by block shows the correct signer's real drawn signature + full name + their own approval date (not the month-close date, not another signer's). Re-download returns the identical archived file, not a freshly re-rendered one (should be instant).
If a value looks wrong, check it against the exact SRD table (§2.2.10 FMC / §2.2.11 MMSDA) before filing — several fields (vendor bank name/account/contact) legitimately differ between FMC and MMSDA.

04 Security & session — worth your own hands-on time

This app has no login form of its own — it fully trusts a hand-off from core. These aren't in the SRD (it's a functional spec), but a hole here is account-takeover-class, not cosmetic, so they're first-class test cases, not an afterthought.

  • Replay a used SSO hand-off URL
    Open a fresh hand-off link from core, then open the exact same URL a second time (e.g. via browser history). Expect: 401 "Token already used" on the second open — never a second successful login.
  • Cross-app logout propagation
    Open BackOffice in one tab, log out from core in another tab, then refresh the BackOffice tab. Expect: it does not still render the listing — you're bounced to re-authenticate, not left on a stale authenticated page.
  • Logout the other direction
    Click Logout from inside BackOffice. Expect: you land back on core's own login/home, and a subsequent direct hit on a BackOffice page requires a fresh hand-off.
  • Idle-timeout bounce
    Leave a BackOffice tab idle past the session timeout, then click anything under /admin. Expect: a clean re-auth bounce back through core — no dead-end error page.
  • Hand-off for a user with no role at all
    Use a core account that has no Association Payment role mapped. Expect: 403 "No access to this module" — the SSO hand-off itself succeeds (real login), only the module authorization fails.
  • H1 (in fix, re-test once landed) — cross-module role confusion
    If any other BackOffice module ever shares a bare role name (e.g. a generic DRAFTER), a session authorized for that other module must NOT be able to act on /admin/association/**. Not independently reproducible today with one module live — re-check the fix CR's own dedicated test/proof once it lands, and spot-check that a legitimately-scoped Association user still works normally afterward (no regression).
  • H2 (in fix, re-test once landed) — open redirect on session-expiry/logout
    Trigger the session-expiry bounce (idle-timeout case above) and the logout redirect. Expect both to land only on a trusted core origin — never an attacker-controlled off-site URL, even if one could theoretically be crafted into the flow. Confirm the ordinary same-origin case still redirects correctly (no regression from the fix).
  • Concurrent double-submit (two tabs, same action)
    Open the same month's details in two tabs as the same approving user; submit the same action from both. Expect: the second submit gets 409 "someone else already actioned this, please refresh" — never a silent double-write, and only one audit-log row is created.

05 Cross-cutting checks — beyond the SRD's happy path

Month-close idempotency

  • Close an approved month once → 200 CLOSED.
  • Close the exact same month again immediately → 200 SKIPPED_ALREADY_CLOSED, and the underlying DB row is unchanged (ask a dev to confirm a before/after diff if you can't query directly).
  • Try closing a month that hasn't reached full approval yet → 409 SKIPPED_NOT_APPROVED, not a silent no-op or a 500.

Storage sanity (ask a dev to confirm the DB side)

  • A user's signature is stored exactly once, referenced by object key — never re-drawn or duplicated across months.
  • Downloaded PDFs are byte-identical on repeat download (served from the archived object, not re-rendered each time).

Out-of-role / out-of-sequence actions

  • An Approver-only account attempting a Drafter action (e.g. by guessing/replaying a request) → 403, never a silent success.
  • Any action attempted on a month that's already fully approved (terminal state) → rejected, not accepted as a new transition.

Numbers tie back to core

  • Pick one state + vehicle type for a closed month; manually cross-check the count against core's Transaction Summary Report by State for the same JPJ-approved-date window. They should match exactly — this module never invents figures.

07 Reporting a bug

What makes a report actionable here

Reference the exact requirement ID (e.g. "REQ-013 case 3") or security case you were running, the test user/role you were logged in as, the month you were testing against, and what you expected vs. what happened. If you have console/network output, attach it — several of these flows return specific HTTP status codes (401/403/409) that are meaningful on their own.

File against EAINT-12028 (or a linked sub-ticket per your team's convention). For anything under § Current status's active fix items (B1/H1/H2/M1–M7), check with the dev first — it may already be fixed on a commit newer than what you're running.
